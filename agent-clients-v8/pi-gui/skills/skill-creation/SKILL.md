# Skill Creation

1. For tool work, record the plan after preparing the brief. Give each step a `skillQuery` describing its main technique or explicitly requested standard. Search the installed library with `find_skills` for the in-progress step. Try a meaningful synonym if the first search is weak. When the user names a skill, search for it directly. Read applicable skills with `use_skill`. Read a listed reference only when it affects the task.
2. Reuse a suitable skill as written. If a check disproves a step or factual claim in a skill you used, preserve the prior revision and use `save_skill` to record the verified correction. Avoid skill edits for one-off preferences. Advance the plan before starting a distinct stage. Pi checks the new step's query and asks you to resolve any changed skill route before work continues. Find and load the relevant skill without waiting for the user. Reuse the same query across steps covered by the same skill.
3. When a reusable procedure has no good local match, use `research_skill` if available. Prefer official documentation, maintainers' repositories and reproducible examples. A query naming one RFC opens its official text directly. Read the relevant continuation if the needed rule or example is missing. Compare sources when the evidence conflicts or remains weak. When the tool is disabled and the required standard has no local skill, ask for a local skill. A search snippet alone is insufficient evidence.
4. Stop once the opened source establishes the procedure and a check that can independently catch a wrong result. One authoritative source can be sufficient. Prefer a published example, known fixture or already available tool when it can verify the result. Record any boundary case that can change the output. If one probe has established a fact, another way to run that same probe adds little evidence. Look for a published test vector when an observed result conflicts with memory. Deliver each verified output when it is ready. If a new package is necessary, confirm its exact registry identity and purpose from its maintainer's documentation before installing or importing it. Keep research within three searches and five source pages per task.
5. Use `save_skill` to draft the smallest useful guide. Include when to use it, actionable steps, and a check for the rule most likely to change the result. Load the draft and apply it. Compare the actual result with the authoritative passage, and revise and reload the draft if any claim disagrees. Before marking the plan complete, call `publish_skill` with the `verificationReceipt` number shown in the passing tool result and the exact supporting source excerpt when the draft cites research. Published skills are available in future chats. Use the discard option when a draft cannot be verified.

When the exact bytes, ordering or formatting matter, compare that representation directly. Load reference test data from its source where possible. Keep fixtures as data files, especially when they contain escapes, and run saved code with `run_script` so the shell does not reinterpret the script or arguments. Inspect a failed test in isolation before running another patch-and-test sequence. When a command or dependency appears in the guide, establish its identity and intended use before recommending it.
6. For routine conversation, a simple question, or work with no reusable workflow gap, load `general-task`. If the requested task forbids web access or research is unavailable, reuse a fitting local skill or use `general-task` and state the relevant limitation. Avoid inventing evidence or installing unreviewed remote content.
